# 室内非 GNSS 硬件自检

- 日期：2026-11-11（Asia/Hong_Kong）。
- 对应步骤：硬件验收第 1 节“单节点硬件”，为实施计划步骤 3–6 的前置检查；传感器故障排查进行中。
- Git 基线：`b26aaee`（`codex/e870-8-node`），本轮开始时工作区无改动。
- 测试条件：用户明确说明处于室内且 GNSS 无卫星信号，本轮单独检查其他初始化项目；正式采集仍遵守原 GNSS/PPS、32 kHz 时钟和协议配置。

## 做了什么

1. 阅读根目录计划和当前传感器/节点启动代码，检查 Windows USB 与串口枚举。
2. 识别到 COM8，VID:PID=303A:1001，使用 460800 波特率。先收到一条 state=5 的周期状态。
3. 按本机已安装 esptool 的 Windows usbser 控制线传播方式触发 USB 复位；收到 ROM 的 `USB_UART_CHIP_RESET`、完整 BOOT、READY 以及后续三条状态，整个启动捕获期间未出现串口读取错误。
4. 对照当前启动逻辑确认传感器检查在 GNSS 初始化之前执行，GNSS 无卫星信号不会直接使 sensor 自检变为 0。
5. 更新计划和验收记录，按规则删除已提交的上一轮报告，仅保留本轮报告。

## 验证结果和边界

| 项目 | 结果 | 能确定的范围 |
|---|---|---|
| MCU/USB/固件启动 | 通过本轮检查 | 串口通信正常完成此次捕获，固件组合、版本和节点编号与预期一致；不等于长期供电稳定性验收 |
| IIM42652 自检 | 未通过 | sensor=0，可能是 SPI 识别/配置失败，或启动后未同时满足 DRDY 中断与 FIFO 数据检查；现有日志不能继续区分，不能据此判断器件损坏 |
| LoRa 初始化 | 按 tx 环境为通过 | radio=1；此前给出的烧录环境为 eora_s3_400_iim42652_tx。USB 测试环境会跳过实际 LoRa 初始化，BOOT 本身不含此环境标记；本轮未做无线收发验证 |
| 32 kHz 输出初始化 | 通过 | clock_output=1；无法仅凭该字段验证传感器引脚处的波形、连线、占空比或频率精度 |
| GNSS/PPS 与时钟精度 | 待实测 | 用户在室内无信号，gps=0、clock_ok=0；不能据此认为其他硬件损坏，ppm=0.00 也不是校准通过证据 |
| XYZ 数据与 50 Hz 采集 | 待实测 | 未启动采集，队列和丢失计数为零不能证明实际采样通过 |
| 编译/软件测试 | 本轮未执行 | 固件和上位机源代码均无修改；与本次实机检查结果分开记录 |

传感器检查链路：`clock_.begin()` 成功后调用 `sensor_.begin()`，驱动需通过 WHO_AM_I=0x6F、复位后识别和配置读回；随后启动约 120 ms，要求 INT1 的 DRDY 边沿计数增加且 FIFO 中有数据。当前只能确定这条链路未全部通过，不能说 SPI 本身已经通过。
