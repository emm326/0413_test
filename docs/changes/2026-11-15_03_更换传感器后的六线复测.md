- 日期：2026-11-15（Asia/Hong_Kong）。
- 对应步骤：传感器身份恢复的前置硬件隔离测试；主计划步骤3-6仍为待实测，步骤7待开始。
- 状态：已完成（COM8串口复测）；待实测（传感器端供电与SPI线路核查、稳定身份和后续采样）。
- Git基线：`1c2cb94`，分支`codex/sensor-recovery-20261114`。
- 设备：COM8，USB VID:PID `303A:1001`，SER `90:DA:72:76:1F:30`，EoRa-S3-400TB/IIM42652/节点1003。

## 做了什么

1. 用户已更换新的IIM42652模块，并按六线方式连接。现场六线为VCC、GND、SCK、MOSI、MISO和CSB。
2. 本轮没有重新烧录，继续使用已烧录在COM8的`eora_s3_400_iim42652_six_wire`诊断固件。
3. 打开COM8，以460800波特率发送`SCAN`，等待完整`SCAN_END`。
4. 程序只读取`WHO_AM_I`，不写传感器寄存器，不发送软件复位，不初始化LoRa、GNSS、INT1或CLKIN。

## 判断与限制

新传感器消除了旧结果中的CS持续低电平问题。ESP32的CS、SCK和MOSI现在都能正常输出并回读，因此当前不需要改用GPIO35备用CS，也不应继续修改采样驱动。

MISO在内部下拉时仍为1，说明模块端存在外部上拉、持续高电平或其他未预期的线路状态。SPI时钟期间32次读取仍为0，说明身份链路还没有建立。现有证据不能区分以下原因：

1. 模块端VCC或GND没有真正到达传感器芯片；
2. MISO或MOSI在模块端接反、未压紧或接触不良；
3. CSB没有到达传感器芯片，模块仍未被选中；
4. 模块板级电路在MISO上增加了上拉，但芯片没有正常响应；
5. 新模块本身仍有故障。

因此，本轮不能判定新模块已经工作，也不能据此确认传感器损坏。构建和串口能工作不等于传感器身份测试通过。

## 下一步

1. 完全断电后，在传感器模块端测量VCC到GND，确认约为3.3V。
2. 在运行`SCAN`时，在模块端确认CSB从约3.3V降到约0V。
3. 检查模块端的MISO和MOSI是否接反，并重新插紧六根线。
4. 用示波器或逻辑分析仪确认一次读取有16个SCK时钟脉冲、MOSI发送`0xF5`和dummy字节、MISO返回`0x6F`。
5. 在模块端确认MISO没有对VDD或GND短路，并记录模块正反面照片、购买链接或商家引脚说明。
6. 只有WHO_AM_I稳定返回`0x6F`后，才接回INT1和CLKIN，再恢复正式固件和采集验收。
