# 室外 GNSS 与 PPS 诊断

## 对应步骤

阶段 4～5 的第一步：验证室外 GNSS 定位、PPS 秒脉冲和正式采样启动门槛。

## Git 基线

- 基线提交：`a4b04ee`（docs: 更新项目特点与室外GNSS测试计划）。
- 分支：`codex/sensor-recovery-20261114`。
- 本轮新增 PPS 诊断接口，代码和本报告随本轮提交。

## 做了什么

1. 在 `GpsTimebase` 增加原始 PPS 边沿计数。
2. 在串口增加 `GPS_DIAG` 命令，输出定位、PPS、UTC 映射、PPS 间隔和异常计数。
3. 使用 COM8、460800 波特率，每隔 2 秒查询一次，连续观察 30 秒。
4. 用户确认设备位于室外，GNSS 模块的 PPS 指示灯正在闪烁。
5. 查询 `STATUS`，核对正式采样的 GNSS 和时钟门槛。

## 接线与烧录

- 接线不变：GNSS RX 接 GPIO16，GNSS TX 接 GPIO15，GNSS PPS 接 GPIO41。
- GNSS 与开发板共地。
- 测试固件：`eora_s3_400_iim42652_usb_test`。
- 端口：COM8；串口：460800。
- 烧录后的 Hash 校验通过。

## 验证结果

### GNSS 与 PPS

30 秒内多次查询均得到：

```text
GPS_DIAG,fix=1,pps=1,time=1,healthy=1,
pps_interval_us=999980..999983,
pps_bad=40122,timer_jumps=0
```

- `fix=1`：GNSS 已输出有效定位。
- `pps=1`：当前 PPS 间隔有效。
- `time=1`：PPS 已与 UTC 建立时间映射。
- `healthy=1`：当前 GNSS 时间基准健康。
- PPS 间隔约为 `999981 µs`，符合 1 Hz 秒脉冲。
- `pps_bad` 在观察期间保持 `40122`，没有继续增加；这些记录来自模块锁定前的历史噪声边沿，不是当前持续故障。
- 每 2 秒查询一次，原始 PPS 计数增加 2，符合 1 Hz。

### 正式采样门槛

同一时间的 `STATUS` 为：

```text
STATUS,id=1003,state=1,gps=1,clock_hz=22.9167,ppm=-999283.88,clock_ok=0,queue=0,lost_samples=0,lost_packets=0
```

结论：

- GNSS 定位和 PPS 锁定已通过第一步验收。
- 正式采样仍被 `clock_ok=0` 阻止。
- `clock_hz=22.9167` 和 `ppm=-999283.88` 是在 GPIO36 外部 32 kHz 不可用时得到的无效测量，不代表 IIM42652 内部时钟频率。
- 当前传感器已回退到内部时钟。下一步应让时钟门槛区分“外部 CLKIN 测量”和“传感器内部时钟”，不能在内部时钟模式下继续要求 GPIO36 的 32 kHz 测量。

## 当前边界

- 本次只验证 GNSS/PPS 和启动门槛，没有启动正式 50 Hz 采样。
- 没有发送 LoRa 数据，不能据此宣称空口链路通过。
- 本轮没有修改接线、传感器配置、节点 ID 或上行频率。

## 下一步

1. 修正内部时钟模式下 `clock_ok` 的判定和状态含义。
2. 确认 `gps=1` 时正式 50 Hz 采样可以稳定启动。
3. 连续运行 60 秒，检查样本数、FIFO 故障和时间戳。
4. 接入 E870 网关，验证 STATUS 和 SAMPLE 实际上行。
