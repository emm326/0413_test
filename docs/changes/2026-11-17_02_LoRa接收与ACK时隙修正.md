## 结论

1. LoRa 上行可用。网关完整收到节点 DATA：30 秒测试收到 60/60 个唯一包（100%），60 秒测试收到 119/120 个包（99.2%）、2971/3000 个样本（99.0%）。RSSI 平均 -22.0 dBm，SNR 平均 10.3 dB，网关无效包 0。
2. ACK 原先收不到的根因是发射时隙，不是射频链路。E870 在 31 ms 内返回 TX_ACK，说明它已接受下发指令；但实际空口发射比主机下发晚约 400 ms。节点只在每个 5 秒周期的 4.000～4.250 s 监听 ACK，原调度在 4.03～4.10 s 下发，空口到达约 4.43～4.50 s，已经超出监听窗口。
3. 修正后网关在 3.68～3.82 s 下发 ACK，空口到达约 4.08～4.22 s。30 秒和 60 秒测试都实现 ACK 确认、重传 0、最终 `state=1`、`queue=0`。
4. 补传链路同时验证通过。一次测试中网关提前退出，节点积压 112 包；网关恢复后按已保存序号逐轮 ACK，队列降到 0，run 7029 的 119 个包全部收齐，`lost_packets=0`。

## 做了什么

1. 做 ACK 时隙扫描：在 3.45～4.28 s 之间按不同节点相位逐轮下发 ACK，记录节点 `FLOW.rx` 和 `FLOW.ack` 的增量。
2. 实测网关下发往返：连续 3 次发送 ACK，TX_ACK 在 0～31 ms 内返回，证明延迟发生在网关内部发射排队，不在网络。
3. 修改 `host/gateway.py`：新增 `ACK_TX_LEAD_US=400000`，把 ACK 请求窗口从 4.03～4.10 s 改为 3.68～3.82 s，目标是空口到达 4.08～4.22 s。
4. 更新 `tests/test_e870_8_node.py` 的相位断言，使其对应当前 ACK 调度。
5. 未修改固件、接线、节点号、频率、扩频因子和采样率。

## 验证结果

### ACK 时隙扫描

下表为“主机记录的下发相位”和节点是否收到 ACK。相位由节点 `FLOW.phase` 推算，主机读取串口约有 10～20 ms 延迟，因此数值有同样量级的不确定度。

| 下发相位（s） | 节点收到 ACK | 说明 |
|---:|---|---|
| 3.454 | 否 | 空口到达早于 4.000 s |
| 3.565 | 否 | 仍在窗口之前 |
| 3.626 | 是 | rx+1、ack+1 |
| 3.673 | 是 | rx+1、ack+1 |
| 3.769、3.773 | 是 | 重复验证均通过 |
| 3.800、3.807 | 是 | 重复验证均通过 |
| 3.815 | 是 | 该轮 rx+2、ack+2，相邻探测帧落入同一统计窗口 |
| 3.892、3.894 | 否 | 已越过 4.250 s 窗口上边界 |
| 3.957、3.990、4.053 | 否 | 到达时间晚于窗口 |

结论：可用下发带约 3.60～3.86 s，宽度约 250 ms，与节点 ACK 监听窗口宽度一致。由此推算 E870 的实际发射延迟约 0.39～0.40 s。

### 补传恢复（run 7029）

测试脚本因读取到启动前的旧 STATUS 行而提前退出，网关停止约 45 秒，节点积压 112 包。网关恢复后按“只确认已写入 CSV 的序号”逐轮 ACK：

```text
queue: 112 -> 88 -> 49 -> 16 -> 1 -> 0
final STATUS,id=1003,state=1,...,queue=0,lost_samples=0,lost_packets=0
```

网关最终保存 119 个唯一包（序号 0～118），与节点本轮生成数量一致。
