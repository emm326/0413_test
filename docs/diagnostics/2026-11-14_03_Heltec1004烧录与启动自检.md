# Heltec1004烧录与启动自检

- 日期：2026-11-14，Asia/Hong_Kong；对应步骤3/4/5的Heltec单节点硬件检查。
- 状态：待实测（本轮烧录、日志读取已完成，传感器启动自检执行但未通过）。用户已确认传感器/GNSS接线完成、COM6接入并明确授权烧录。
- Git基线675a49a，分支codex/sensor-recovery-20261114；保留并完成前轮UART0修正及接线指南，本阶段按项目规则提交相关配置和文档。

## 1. 做了什么

1. 枚举确认COM6为CP210x（VID10C4/PIDEA60/序列0001），再通过只读esptool核对ESP32-S3、8MB Flash、MAC9c:13:9e:9d:e8:a8，确认与前轮COM8/EoRa不是同一芯片。
2. 使用现有环境heltec_v32_iim42652_usb_test，节点默认1004，构建并只对COM6烧录。程序/引导相关段写入后Flash摘要校验通过。
3. 立即以460800波特读取完整BOOT及启动自检，再发送DIAG/STATUS验证运行期身份。未发送START，没有连续采集，也没有操作网关。
4. 烧录后所有测试串口均关闭释放。

## 3. 接线与烧录

沿用Heltec固定传感器SCK47/MOSI48/MISO33/CS34/INT1=26/CLKIN=3，GNSS TX→5、RX←6、PPS→4，共地与原供电入口保持。用户已确认连线；本轮没有要求改线。

USB自检固件：348176字节，SHA256 `a80583a4c25367c8a6ffbb70db2951f100ee3872386fe1977897f5bd41c1f3ee`。目标1004/uplink470.9/clock32000/packet180。USB模式跳过Radio::begin/收发，READY中的radio1是占位就绪，不算无线通过。

## 4. 验证结果

| 环节 | 结果 | 实测 |
|---|---|---|
| 软件准备 | 通过 | Heltec USB自检、Heltec正式、EoRa正式三个环境构建通过 |
| 串口类型静态验证 | 通过 | Heltec NodeApp引用HardwareSerial::begin；EoRa引用HWCDC::begin |
| COM6烧录 | 通过 | PlatformIO SUCCESS，Flash写入摘要校验通过 |
| UART0控制台 | 通过 | 完整BOOT/DIAG/STATUS可读，board Heltec V3.2 LF、id1004 |
| 传感器身份 | 未通过 | expected0x6F，actual0x00；模式0/3、100kHz/1MHz后续也0 |
| 传感器软件复位 | 本次未执行 | 首次身份检查失败即返回，日志无SENSOR_RESET |
| 启动采样自检 | 未通过 | init0/ok0，READY sensor0 |
| 板端时钟输出 | 有边沿 | 200ms clock计数6402/6398/6399，尚非外部精度验收 |
| GPIO26中断输入 | 异常 | 相应200ms边沿6402/6398/6399，与GPIO3时钟同数 |
| MISO空闲读值 | 与EoRa历史不同 | 无/下/上拉下digitalRead均1，SPI WHO仍0；不能当有效应答 |
| 故障保护 | 生效 | state5，drdy_interrupt_disabled1/capture_blocked1；之后edge_delta0，queue0 |
| GNSS/时钟精度 | 待实测 | 本观察窗口gps0/clock_ok0，未有连续PPS校准结果 |
| 连续采集/无线 | 待实测 | 本轮未启动50Hz、未测试无线ACK/STOP |

SENSOR_CHECK中的drdy0/fifo0/clock_edges0来自sensorInit失败后未运行120ms窗口的默认值，不能误解为板端时钟没有输出；后面的INT_PULL_DIAG实际计到了时钟。

最后状态：`STATUS,id=1004,state=5,gps=0,clock_hz=0.0000,ppm=0.00,clock_ok=0,queue=0,lost_samples=0,lost_packets=0`。

本轮是在另一块芯片、另一套GPIO映射上观察到与1003历史相似的“身份0、中断输入跟随时钟”现象。它是新的对照证据，但不能单凭此判定模块损坏、两块主控损坏或用户接线错误。用户只授权本轮烧录及其启动检查，没有据此擅自继续接口恢复/改线/正式采集。
