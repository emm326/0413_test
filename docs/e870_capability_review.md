# E870-L470LG12-O 统一启停与并行采集能力核查

初始核查日期：2026-11-07；设备只读深度核查更新：2026-11-12（Asia/Hong_Kong）。对应计划第 3、4、5、6 步。设备服务和管理连接已核查，项目射频与采集验收仍为待实测。

## 2026-11-12 现场补充与纠正

已通过 USB2 读取设备实际配置、运行日志和自带源码，详见 [本轮检查报告](diagnostics/2026-11-12_02_E870频段与程序深度检查.md)。

- 厂家标称工作频率为 470–510 MHz；设备 SX1250 驱动源码亦包含这一频段的镜像校准分支。现行 CN470 配置的 500–510 MHz TX 上下限是 Packet Forwarder 从 JSON 读取并执行的允许范围，不能将其等同于硬件只支持 500–510 MHz。
- 设备 Packet Forwarder 下发处理链支持 SF5/SF6、125 kHz 和原始 payload 转发；此版本 HAL 对 SF5/SF6 的收发使用私有同步字 0x12，即使 `lorawan_public=true` 也是如此。之前仅按公共/私有开关推断 SF6 不兼容的表述须纠正。
- 这些是产品资料、设备配置和源码证据。未发 470.3 MHz，未测 PA/滤波、功率与实际节点回复；不能标为无线验收通过，也不能仅修改 TX 上下限冒充验证。
- 当前原厂服务 active/running、没有自动重启；有线 IPv6 SSH 管理入口能响应。设备无 eth0 IPv4，转发目标仍为本机 127.0.0.1，项目的 IPv4 UDP 路径未通。

## 1. 结论

可以用这台设备搭建“统一预约开始、八节点分信道并行上传、停止采样后补齐尾包”的系统。它负责无线收发和网络转发，具体采样、同步、启停、确认及文件保存由 ESP32 节点固件和电脑上位机共同实现。不能把出厂的 ChirpStack 下发示例等同于已具备本项目的采集流程。

厂家产品页明确把带 `-O` 的 E870-L470LG12-O 标为半双工。多个节点可以在不同上行信道发送，但网关下发控制时须预留停止上行的窗口。传感器可在该窗口内继续采样和缓存。

| 需求 | 判断 | 条件或实际边界 |
|---|---|---|
| 一次操作启动全部目标节点 | 可实现 | 下发未来 UTC 开始时间、运行编号和目标节点集合，逐节点确认 |
| 所有节点从同一时间门限记录样本 | 可实现，待实测 | 节点 GNSS/PPS 正常；需测首样本时间和采样相位差 |
| 八节点同时上传 | 分信道方案有硬件基础，待实测 | 8 个 125 kHz 信道，网关固件启用 SF6/SF5，链路容量及干扰满足要求 |
| 所有节点在同频、同 SF、相同时间发送不同数据 | 不能作为可靠设计 | 应使用不同信道或时隙；集中器并发能力不等于任意同信道碰撞都可解码 |
| 到约定时长自动结束 | 已有软件逻辑，待实测 | 使用相同开始时间和时长；严格时间终点还需按样本时间戳过滤 |
| 按按钮立即同时停止 | 当前不能保证 | STOP 在控制窗口发送，执行受接收成功、重发和主循环时延影响 |
| 停止后完整保存 | 已有收尾逻辑，待实测 | 停止采样后继续传尾包和补传，全部队列清空且状态确认后才结束运行 |

## 3. 项目当前实现及边界

- 上位机 `host/gateway.py`：广播 START，包含统一未来 UTC、时长和节点掩码；收齐 CONFIRM 后在主机判为启动成功。未验证原厂配置支持 470.3 MHz 下行时，禁止发起采集。
- 节点 `firmware/common/app/NodeApp.cpp`：接受 START 后进入 Armed；提前预热传感器，只保留开始门限之后的样本。PPS 和外部采样时钟有同步基础，但当前逻辑没有保证各传感器的 DRDY 相位完全一致；同步误差必须实测，不能声称微秒级同步。
- 8 个节点上行固定为 470.3、470.5、470.7、470.9、471.1、471.3、471.5、471.7 MHz；不是让八个节点在同一信道同一 SF 硬碰撞。
- 五秒周期已有正常上传、公共控制、并行回复和补传四个阶段，适合半双工网关。实际保护时间与空口耗时待实测。
- `durationSeconds` 非零时，节点到共同结束门限调用 `stop()`。但 `acquire()` 目前只检查开始时间，且在停止前读取 FIFO，因此结束边界可能包含终点之后的样本。如需严格相同的采集区间，应将有效样本限定为 `[T0, T0 + duration)`，并验证边界附近 FIFO 和 DRDY 行为。
- 手动 STOP 由上位机排入控制窗口。无线丢包时需要再次操作或后续可靠重试设计；当前实现不能证明一次点击必达，也不能把本地停止网关或关闭上位机当作节点停止。
- `stop()` 会停止传感器、封装尾包，再进入 Draining，待 ACK 清队列后回到 Waiting。上位机等待全部目标节点处于本次运行的 Waiting 状态才清理运行信息。应允许停止采样后继续收包，避免截掉尾部数据。
- 全节点确认是主机的成功判据，并非原子提交协议：节点收到 START 即预约启动。若该节点 CONFIRM 丢失且主机取消 STOP 也丢失，仍可能有节点启动。如要求“全部启动或全部不启动”，需要补充许可/租约或两阶段机制及失联故障测试。

## 4. 建议的正常操作流程

1. 导出 E870 原厂配置，查明 TX 射频通路、470.3 MHz 发射范围，以及 SF6/SF5 的实际支持。
2. 发现节点，确认全部目标节点 GNSS/PPS、采样时钟、传感器就绪。
3. 广播未来的 `T0` 和本轮运行编号，收集全部目标节点 CONFIRM。
4. 到 `T0`，各节点依据本地授时开始记录；在各自上行信道上传，控制窗口内继续采样和缓存。
5. 固定时长任务优先在 START 中预先下发时长。需要提前结束时，按控制窗口发送 STOP，并逐节点确认停止及队列状态。
6. 等待尾包、补传和 ACK 完成，再关闭本轮文件并核对样本数量、最终缺失率和结束边界。

## 5. 尚待实测

- 470.3 MHz 实际下行成功及每个节点的 CONFIRM；TX_ACK 不能替代节点确认。
- 8 个信道同时 SF6 上传、公共控制时段的收发切换、ACK 覆盖及队列无持续增长。
- 首样本时差、稳定采样相位差、定时时长终点偏差、手动停止延迟和尾包完整性。
- 启动确认丢失、取消 STOP 丢失、人工 STOP 丢失、节点断电及上位机退出等故障行为。
- 1→2→4→8 节点 50 Hz 扩容和两小时验收；100 Hz/SF5 仍以前一阶段通过为前置条件。
